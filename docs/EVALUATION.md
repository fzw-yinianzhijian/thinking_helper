# 验收与回归

## 状态约定

当前表格定义待验收场景，不能据此宣称通过。每次运行记录日期、代码版本、模型配置、环境、步骤、实际结果及失败证据。区分模拟测试、真实 API 测试与用户体验；三者不能互相替代。

## 持久性

| 场景 | 通过条件 |
| --- | --- |
| 服务重启 | 已提交项目版本与任务仍可查询 |
| worker 退出 | lease 过期后可恢复，不永久卡在运行 |
| 重复领取/提交 | 候选只合并一次，版本不重复增加 |
| 预算耗尽 | 有明确终态，不继续消耗模型调用 |

## 对话与整合

| 场景 | 通过条件 |
| --- | --- |
| 用户改口 | 新表述生效，旧内容保留来历 |
| 后台晚到 | 旧基准候选不能覆盖新决定 |
| 人工拒绝 | 当前工作区不变，候选可追溯 |
| auto-apply | 仅显式启用且无冲突时应用 |

## 语音体验

使用中文解释、数字密集内容、停顿、改口和打断样本。记录用户结束发声至首个可听回复、取消后残余声音、识别纠正与失败恢复。报告分布及样本条件；不预填延迟成绩，不用单个 TTS 首包代替端到端体验。

## 汇报与连续性

给系统一个持续问题，分两天补充及推翻信息。检查汇报能否说清目标、当前结构、新证据、变化原因和未定问题；用户应能追问定位并纠正。引用必须指向实际来源，推断不得冒充用户确认的事实。

## 后台价值

离开前留下一个值得继续的问题。后台输出须说明读了什么、发现了什么、改变了哪个判断、为何现在值得看。无新增价值时允许不通知。先与同样材料的单次摘要比较，人工判断是否减少重复、补上关键依据。

## 自更新回归

先重现失败，再建立候选策略；使用同一组案例比较当前与候选。至少检查改口、冲突、错误来源、预算、短汇报和停机恢复。保存逐例差异及成本；平均分改善但核心场景退步时，不自动替换。

## 必须留白的结果

首次验证前，音色自然度、实网延迟、真实 API 费用、远端重启恢复、长期记忆准确率和用户留存均为未测。外部文档提供能力线索，不能填写这些结果。已测结果只在交接记录引用实际命令与证据。

## 已有的失败样例

首轮计划冒充研究、来源ID冒充原文、外部能力冒充部署、短附和抢话、停止开麦丢尾句、迟到刷新覆盖主题。分别保留真实记录或定向回归；单测证明指定合同，不替代真实场景与跨天价值。

## 方法评估命令

运行 `python -m scripts.evaluate --checks core planning provider api voice`。输出data/evaluations中的JSON与system.evaluated事件；无实际不同版本基准只能baseline_only。失败、超时、零测试或检查中源码变化都checks_failed。不会执行模型提供的命令。

## 下一轮用户体验

同一问题做三轮：半形成口述→离开后新证据→回来30秒汇报并打断→拒绝并给原因→再次接续。比较重述、分支丢失、审阅时间、实际端到端延迟和同类错误。已有平台作基线，真实体验前不填成绩。
